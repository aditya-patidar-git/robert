Purpose:  This document describes —at production level of detail —the web -based, 
multi -agent phone -answering platform we want Emergent AI’s engineering team to build 
and test end -to-end. It specifies goals, scope, architecture, models, tools, security controls, 
admin  functionality (including a full user -management system), CI/CD and acceptance tests. 
Where behaviour depends on platform features, we ground it in current OpenAI & Twilio 
documentation and UK compliance guidance.  
 
0) Guiding Principles   
 
1) Production -grade:  No delivery until all automated tests and manual acceptance checks 
pass 100% twice in a clean, production -like environment (see §14 Acceptance).   
2) Zero -hallucination policy:  Answers spoken by the agent must be **grounded in tools or 
our KB** (OpenAI File Search) or else the ag ent asks a concise clarifying question or offers to 
transfer. Implement an **uncertainty gate** that only allows “confident” answers when 
retrieval confidence and provenance are above threshold; otherwise fail closed.   
3) Secrets:  No hard -coded keys in code, prompts or logs. Secrets are vaulted and injected via 
environment variables only; app fails fast if a required secret is missing. Follow OWASP 
**Secrets Management** and **Logging** guidance (PII masking).   
4) Privacy & UK compliance:  Provide lawful b asis, notice and controls for recording; DSAR 
export/deletion; retention schedules; CLI presentation; PECR rules for marketing calls 
(TPS/CTPS). See §12.  
 
1) Goals & Outcomes  
 
- Primary goal:  A live, SIP -connected speech -to-speech agent (“Robert”) that answers our UK 
number in <2 seconds, converses naturally, uses **OpenAI gpt -realtime** for audio in/out,

4) High -Level Architecture (Multi -Agent)  
 
Ingress (SIP First, Streams Fallback)    
- Primary:  **Twilio Elastic SIP Trunking → OpenAI Realtime SIP** (low -latency PSTN 
integration).   
- Fallback:  **Twilio Media St reams** (`<Stream>` WebSockets) to our Voice Gateway, which 
bridges audio to OpenAI Realtime Client API and returns TTS back to Twilio.  
 
Agents & Services    
- **A1: Call Agent (Realtime)** — **OpenAI `gpt -realtime`**, full -duplex audio, 
function/tool calling, barge -in, VAD turn -taking, multilingual. Model runs with **system + 
developer prompts** and tool declarations.   
- **A2: Transcriber** — selectable **`whisper -1`** or **`gpt -4o-transcribe`** for 
parallel/after -call transcription and summarisation. (Model selection in Admin.)   
- **A3: KB Retrieval** — **File Search** tool on our OpenAI vector store 
(UNIVERSALAIDATABASE). (Nightly re -ingest; tags; drift detection.)   
- **A4: Browser Agent** — **Headless Playwright** worker to operate our cloud CRM via 
controlled scripts (dry -run → diff → caller confirm → commit), with DOM as sertions and 
artefacts.   
- **A5: MCP Server(s)** — **mcp.web_search** (Brave), **mcp.calendar/email** 
(optional), **mcp.crm** (optional API facade). Realtime supports **remote MCP servers**; 
expose as tools to the model.  
 
Control Plane & State  
- **Orchestrator API** (Node/TypeScript): Session registry (per Call SID), tool schema 
enforcement (Zod/JSON Schema), uncertainty gate, transcripts, memory, audit logs, 
DSAR/export, retention.   
- **Admin Console** (Next.js/React): Models & voices, audio/VAD, prompts , KB, tools, 
telephony routing, security/privacy, observability, **User Management** (see §10).  
 
Observability  
- **OpenTelemetry** for traces/metrics/logs; link Twilio Call SID to app spans.   
- **Twilio Voice Insights** for call quality, MOS, jitter, packet loss; SLO dashboards.

8) Audio UX (VAD, Barge -in, Padding)  
 
- Turn detection (VAD):  Start with ~**500 –700 ms** end -of-turn silence; adapt per call.   
- Barge -in: If the caller speaks while TTS is playing, stop TTS immediately and resume 
listening (Realtime supports barge -in).   
- Padding:  Inject ~**250 ms** leading and **300 –500 ms** trailing silence on TTS chunks to 
prevent PSTN clipping; tuneable in Admin.   
- Noise control:  Prefer primar y **SIP→Realtime** path to reduce latency; fallback **Media 
Streams** path can apply server -side noise suppression if needed.

10) Admin Console — Comprehensive User Management (RBAC) & Controls  
 
10.1 User & Auth Model (Backend)  
 
- User:  `id (UUID)`, `email`, `username`, `role (owner|admin|user)`, `status 
(pending|active|blocked|excluded|deleted)`, `password_hash (Argon2id)`, `mfa_enabled`, 
`last_login_at`, timestamps. Use **Argon2id** for password hashing, with modern 
parameters configurable i n env.   
- Allowlist:  `id`, `type (email|domain)`, `value`, `notes`, timestamps, `created_by`.   
- AuditLog:  `id`, `actor_id`, `action`, `target_type`, `target_id`, `ip`, `user_agent`, `diff (JSON)`, 
timestamps.   
- Sessions/Tokens:  Signed JWT (short -lived ) + refresh; server -side session store for 
**revocation on status change**.  
 
> **Security defaults:** Argon2id; strict rate -limiting; IP throttles; CSRF for state -changing 
endpoints; **PII redaction in logs**; absolute **secrets in vault**.  
 
10.2 Admin API Endpoints  
 
- `GET /admin/users` — Paginated list; filter by status/role; search by email/username.   
- `POST /admin/users` — Create user (owner/admin only).   
- `PATCH /admin/users/{id}/approve` — Approve pending → active.   
- `PATCH /admin/users/{id}/blo ck` — Block.   
- `PATCH /admin/users/{id}/exclude` — Permanent ban (audit mandatory).   
- `DELETE /admin/users/{id}` — Soft delete (default); `?hard=true` if owner.   
- `GET|POST|DELETE /admin/allowlist` — Manage pre -approval allowlist.   
- `GET /admin/audit` — Paginated audit trail (securely filterable).  
 
RBAC rules  
- **owner**: Full access including hard delete and role changes.   
- **admin**: Manage users (not owners), allowlist, prompts, models; no hard delete of 
owners.   
- **user**: No admin access.  
 
Status transitions  
- `pending → active` (approval); `active ↔ blocked`; `active → excluded` (ban); `* → 
deleted` (soft/hard).   
- On **block/exclude/delete**: revoke all sessions immediately (JWT blacklist/rotation).  
 
10.3 Admin UI (Next.js/React)  
 
- Users Table  with role/status badges; search/filter; pagin ation; row actions with confirm 
dialog; **bulk actions** (block/approve/delete).   
- Create User Modal:  Email, username, role, initial status; client & server validation.   
- Allowlist Manager:  Add/remove email or domain entries with notes.   
- Security:  Owner -only access to Admin; route guards; “view as” is **never** allowed; no 
secrets in client bundle.

13) Detailed Call Flow (Primary SIP Path)  
 
1) Ringing → Pickup B(<2.0 s). **Realtime SIP** session initialised; **system prompt** and 
**session tools** configured (File Search, MCP , Browser Agent).   
2) Greeting & Language:  English male (default **Ash** voice) asks preferred language; 
detect and switch voice/language seamlessly.   
3) Barge -in: If caller interrupts, TTS halts within ~200 ms; VAD resumes listening.   
4) Grounded Q&A:  For polic y/booking queries, **File Search** retrieves sources; agent 
answers with short, grounded wording **and verbal source cue**.   
5) Browser tasking:  For “Move my CBT to next Tuesday 10am”, agent performs **KBA** 
(e-mail + postcode + booking ref or OTP), runs **dry -run**, reads back diff, obtains 
**explicit confirmation**, **commits**, then asserts success; sends SMS/e -mail confirm.   
6) Escalation:  On low confidence or request, transfer to human queue; capture DTMF where 
needed.   
7) Closure:  Summarise outcome ; log structured call record; optionally store **short 
cross -call memory** with consent.

14) Acceptance Criteria & Tests (must pass 100% twice)  
 
1) Pickup:  Inbound answers <2.0 s; greeting played; language request heard; French reply 
triggers immediate switch.   
2) Barge -in: Caller speech interrupts TTS; stop within 200 ms; agent continues.   
3) VAD/padding:  No over -talk; no tail -cut; padding prevents clipping.   
4) **KB retrieval**: A DVSA/CBT policy question returns correct passage via **File Search ** 
and is cited in speech/transcript.   
5) **Web search**: A current, non -KB fact triggers **MCP web_search** with prior 
disclosure (“I’m checking online…”); result grounded and logged.   
6) **CRM tasking**: Reschedule request completed with **KBA**, **dry -run diff**, 
confirmation, commit, **DOM assert success**; confirmation sent.   
7) **Human transfer**: DTMF capture; bridge success.   
8) **Memory**: Preference set in call 1; recalled in call 2 **only after consent**.   
9) **Concurrency**: 20 simultaneous calls; p95 end -to-end turn latency with in target; **no 
cross -talk**; Twilio **Voice Insights** shows acceptable MOS/jitter.   
10) **Error paths**: Inject OpenAI 5xx / Twilio stream drop; graceful apology; retry; 
voicemail fallback.   
11) **GDPR/DSAR**: Export transcript & metadata; delete on request; retention 
respected.   
12) **Security**: No secrets in logs or bundles; password hashing Argon2id; session 
revocation on status change; PII masking.

18) Orchestrator Logic (tool -calling & uncertainty gate)  
 
1) Intent detection:  Ask the model to decide among categories (answer / KB lookup / CRM 
action / web search / transfer).   
2) KB:  If KB -likely, call **File Search** with relevant file set; **reject** answering if 
confidence below threshold.   
3) CRM:  If action requested, if it is an existing client, enforce **KBA** 
(e-mail+postcode+booking ref or OTP via CRM phone) before dry -run. If it is a new client, 
there is no need, as you will be colle cting all the required data to make the  booking from the 
client and input on the CRM (Incontact).  
4) Web:  If time -sensitive and not in KB, disclose “I’m checking online…”, call 
**mcp.web_search** (allow -list + latency budget).   
5) Payments:  If enabled, hand off to **Twilio <Pay>** only; never collect PAN/DTMF.
