## 3. ARCHITECTURAL SIMPLIFICATION: The Service Layer Pattern

### Current Problem
All logic is embedded in WebSocket handlers:
```
/media-stream handler
  → mixed concerns: WS protocol + business logic + state management
```

### Simple Solution: Extract to Service Layer

```javascript
// NEW FILE: services/conversationService.js
class ConversationService {
  async handleUserMessage(message, context) {
    // Pure business logic - no WebSocket concerns
    const intent = await this.detectIntent(message)
    const response = await this.generateResponse(intent, context)
    return response
  }
  
  async handleToolCall(toolName, params, context) {
    // Pure tool execution logic
    const result = await this.executeTool(toolName, params)
    return result
  }
}

// TESTING BECOMES TRIVIAL
describe('ConversationService', () => {
  it('retrieves KB for policy questions', async () => {
    const service = new ConversationService()
    const response = await service.handleUserMessage(
      "What is CBT policy?",
      mockContext
    )
    expect(response.toolCalls).toContain('file_search')
  })
})
```

**What You Gain:**
- ✅ No WebSocket mocking needed
- ✅ No audio simulation needed
- ✅ No timing concerns
- ✅ Tests run in milliseconds
- ✅ 100% coverage of business logic

**What You Lose:**
- ❌ Nothing important (integration covered separately)

## 9. THE ONE TRUTH THAT SIMPLIFIES EVERYTHING

**Stop trying to test the entire system in unit tests.**

Your WebSocket handlers are **integration points**. They should be thin adapters:

```javascript
// WebSocket handler (thin adapter)
async function handleMediaStream(ws, callSid) {
  const service = new ConversationService()
  
  ws.on('media', async (data) => {
    const response = await service.handleAudio(data, callSid)
    ws.send(response)
  })
}

// Everything testable is in ConversationService
// No WebSocket mocking needed
```
